## 1. Summary

STE v0.3 promotes `sources` from an array of free-text strings to a
structured object with a typed enum (`archive | official | news | book
| map | photo | oral_history | dataset | web | other`), gives narratives
a `about_period` time anchor, adds an `ai_assisted` provenance tier
that requires a human `reviewed_by` (closing the "human glanced at it"
loophole), introduces entity-level lifecycle (`ste_status`,
`superseded_by`) with bounded redirect chains, adds a first-class
`coord_provenance` field, and opens three explicit slots on
`contribution_meta` so satellite profiles can attach attribution
signals without a core change. v0.2 documents remain valid: every
change is additive/optional except the version bump itself. Total: 14
new negative fixtures and 6 new application-level rules in the
reference validator.

## 2. Motivation

### 2.1 Why now

Five concrete problems in v0.2 are blocking downstream work:

1. **The attribution ledger is un-buildable** from v0.2 sources.
   `ste-attribution-profile.md` (RFC 0002-candidate) needs to
   aggregate per-source citations; v0.2's `["市教育志"]` strings
   don't de-duplicate or cross-reference.
2. **Liveness checks are partially-deployed** in spirit (validator
   app-level rule 09, `docs/why-rules/why-rule-09.md`) but
   mechanically inert — without a `url` field on the source
   object, the liveness sweep has nothing to ping.
3. **"AI-assisted" is currently laundered as `manual`.** The
   "AI draft → human verifies" workflow is now the modal
   workflow for non-expert contributors. v0.2's enums are
   single-choice; the realistic flow falls into `manual` (the
   human verified) and the AI provenance is lost. R3 of the
   Ethics Charter requires this to be visible.
4. **Merges / splits / duplicates have no schema home.** A
   contributor who notices "this school is the same as that
   school" has no field to mark the duplicate. v0.2 silently
   grows two parallel records; the demo's 89 schools already have
   two such candidates.
5. **`ste-attribution-profile.md` cannot ship** without an open
   `contribution_meta`. v0.2 has `additionalProperties: false`;
   every profile-defined attribution field fails core validation.
   This was caught in review (a CRITICAL blocker for the
   attribution profile).

### 2.2 Supersession

This RFC is the **process-form** version of `docs/proposals/v0.3-core-upgrade.md`,
which already consolidated the technical content from
`docs/proposals/v0.3-entity-lifecycle.md` (superseded 2026-08-28;
the proposal itself documents this). The proposals stay in
`docs/proposals/` as historical record; this RFC is the version
the project tracks for implementation and ratification.

### 2.3 What this RFC does NOT do (deferred to follow-ups)

- **No geometry beyond points.** Polygon footprints remain an
  OHM-side concern. Tracked in `docs/proposals/v0.3-entity-lifecycle.md`'s
  implicit thread; will become a separate RFC when needed.
- **No v1.0 features** (structured evidence cross-validation, entity
  relationships, event model). v0.3 is the additive step; v1.0 is
  the breaking step. The OGC JSON-FG profile (RFC 0003-candidate)
  is the v1.0 work.
- **No schema migration tooling** is included in this RFC's scope.
  The migration is a single-line version bump plus an optional
  string-to-object upgrade of `sources` items; the script ships
  in the implementation PR.

## 3. Detailed design

The v0.3 schema is `v0.3/schema.json` (and `v0.3/schema.zh.json` for
the Chinese mirror, with structural parity CI-enforced). All changes
are additive/optional except the `ste_version` const bump from
`"0.2"` to `"0.3"`.

### 3.1 Structured source objects (§1 of the underlying proposal)

`snapshot.sources[]` items may be:

- **string** — legacy shorthand. Normalized to
  `{ "type": "other", "title": <string> }` for downstream
  processing.
- **object** — the new canonical form. Definition
  `v0.3/schema.json#/definitions/source_object`:

  ```jsonc
  {
    "type": "archive",          // REQUIRED, enum: archive | official |
                                //   news | book | map | photo |
                                //   oral_history | dataset | web | other
    "title": "北京市教育志",     // REQUIRED, non-empty
    "author": "…",              // optional
    "publisher": "…",           // optional (档案馆/出版社/机构/平台)
    "date": "1998",             // optional, ohm_date — publication/issue date
    "url": "https://…",         // optional, format: uri
    "archive_ref": "J001-2-334",// optional — catalogue/call/file number
    "accessed_at": "2026-08-28T08:00:00Z", // optional, date-time (web sources)
    "note": "…"                 // optional
  }
  ```

  Inline constraints:
  - `type=web` ⇒ `url` REQUIRED.
  - `type=oral_history` ⇒ snapshot/narrative SHOULD carry R2 author
    metadata (application-level cross-check).

### 3.2 Narrative time anchor (`about_period`, §2 of the underlying proposal)

New optional field on `narrative_entry`:

```jsonc
"about_period": { "start": "1980", "end": "1989" }
```

- `start` REQUIRED when `about_period` present; `end` optional
  (open-ended = "until the narrator's knowledge ends").
- `ohm_date` for both ends.
- Application rule: `end >= start` after granularity
  normalization (new app-level rule 13 — see §3.7).
- Display rule: narratives render alongside matching timeline
  snapshots; platforms MUST NOT present an unanchored narrative
  as describing the present.

### 3.3 AI-assisted provenance tier (§3 of the underlying proposal)

New enum value **`ai_assisted`** on both:

- `snapshot.description_provenance`
- `narrative_entry.source_of_knowledge`

`ai_assisted` ⇒ REQUIRED:

- `ai_model` (same rule as `ai_generated`)
- `reviewed_by` (`actor_id`, must be `user:` or `community`,
  i.e. a human/accountable party — never `agent:`)
- `reviewed_at` (date-time)

Display rule (R3 unchanged in spirit): `ai_assisted` renders with
the same visual distinction as `ai_generated`, plus the reviewer
identity. The self-reported `confidence` remains REQUIRED and
labeled as generator-reported.

This closes the loophole where "a human glanced at it" laundered
AI text into `manual`.

### 3.4 Entity lifecycle (§4 of the underlying proposal, consolidated)

New top-level fields on the entity document:

| Field | Required when | Notes |
|---|---|---|
| `ste_status` | optional, default `active` | enum: `active` / `merged` / `split` / `deprecated` |
| `superseded_by` | `merged` / `split` / `deprecated`-as-duplicate; FORBIDDEN when `active` | array of `ste_id`s |
| `supersedes` | optional, recommended on the surviving entity | denormalized inverse; tombstone side wins on conflict (same rule as `name`) |
| `ste_status_changed_at` | `ste_status` ≠ `active` | date-time |
| `ste_status_reason` | `ste_status` ≠ `active` | non-empty string |

**Hardening vs. the standalone proposal**:

- `superseded_by` is REQUIRED for `merged` / `split` / `deprecated`-as-duplicate,
  FORBIDDEN when `active`. A `deprecated`-as-*created-in-error*
  record has no successor; it carries `ste_status_reason` only
  (this restores the original standalone scope).
- Redirect chains MUST terminate at an `active` entity within
  depth ≤ 8 (hardened from the original "suggest ≤ 8"; an
  unbounded chain makes consumer behavior undefined).
- Every `ste_status` change is itself a sourced event. When
  `ste_status` ≠ `active`, **top-level** `sources` (structured,
  §3.1) and `contributed_by` are REQUIRED. **These are new
  top-level fields** in v0.3 (v0.2 has `sources` /
  `contributed_by` only at snapshot level). A merge without a
  source is exactly the kind of edit R1 exists to catch.

### 3.5 Coordinate provenance (§5 of the underlying proposal)

Two incidents motivated this (2026-08-26/27): 6 schools geocoded
by guesswork (caught by the owner), and OSM `way center` centroids
silently imported as representative points.

New optional field, at entity level and per-snapshot (snapshot
wins when both):

```jsonc
"coord_provenance": {
  "method": "geocoded",   // REQUIRED enum: geocoded | surveyed |
                          //   interpolated | centroid | approximate | unknown
  "source": { …source_object… },  // optional structured source (§3.1)
  "note": "OSM way centroid, not a curated point"  // optional
}
```

- `method=centroid` or `approximate` ⇒ validator emits a
  warning and UIs SHOULD display low-precision styling.
- Replaces the ad-hoc `ste:coord_confidence` tag with a
  first-class field; the tag remains valid but is deprecated
  in docs.
- `method` is about **how the point was obtained**, orthogonal
  to `confidence` (how sure the contributor feels).

### 3.6 `contribution_meta` field slots (§5A, the unlock for `ste-attribution`)

v0.2's `contribution_meta` has `additionalProperties: false`,
which means **no** satellite profile can attach attribution
signals without a core change (a CRITICAL blocker for
`ste-attribution-profile.md`, caught in review). v0.3 therefore
adds three OPTIONAL field slots to the core definition — the
core provides the **slots**, the `ste-attribution` profile
defines their **semantics**:

```jsonc
"contribution_type": "create",          // enum: create | edit | corroborate |
                                        //   geolocate | oral_history | translate | review
"identity": {                           // at most one of the two sub-fields
  "key_fingerprint": "pgp:9F3C…"        // pattern ^(pgp|did):.+$
  // or: "claim_commitment": "sha256:…" // pattern ^sha256:[0-9a-f]{64}$
},
"rights": {
  "ai_training": "inherit"              // enum: inherit | opt_in
}
```

Inline constraints:

- `identity` allows at most one of `key_fingerprint` /
  `claim_commitment`.
- `contribution_type=oral_history` ⇒ `rights.ai_training=opt_in`
  FORBIDDEN (R9: oral history is permanently excluded from AI
  training, no opt-in).
- All three slots optional everywhere; documents without them
  remain valid.

**Why slots live in core** (not in the profile): profile
documents must pass the core validator. With a closed
`contribution_meta`, any profile-defined field would fail
validation. Opening `additionalProperties` wholesale was
rejected — explicit slots keep "one negative fixture per rule"
enforceable.

### 3.7 New application-level rules (additions to the validator's 12-rule list)

These go into `validator/ste-validator.js` and into
`docs/why-rules/why-rule-NN.md` with the next available
numbers (currently 13–18):

13. **`about_period` end ≥ start** (granularity-normalized
    comparison, same as app-level rule 02).
14. **Bounded redirect chain depth** ≤ 8 (cycle detection +
    depth limit; an unbounded chain is a data-quality bug).
15. **`ste_status` change carries a top-level source** (R1
    applied to the record-level edit, not just the snapshot).
16. **`coord_provenance` method enum** (the enum check; the
    snapshot's `centroid` / `approximate` warning is rendering
    policy, not validator logic — that lives in the demo).
17. **`contribution_meta` identity has at most one
    sub-field** (schema-enforced; validator is the second
    line).
18. **`contribution_type=oral_history` forbids
    `rights.ai_training=opt_in`** (R9 absolute exclusion;
    schema-enforced, validator as belt-and-suspenders).

Total: 12 → 18 rules. The rule-count constant in
`validator/ste-validator.js` updates crosswise with
`docs/why-rules/` numbering.

## 4. Drawbacks

- **Rule-count creep.** 12 → 18 is a 50% increase. The
  reference validator's app-level list is already long; a
  new contributor reading it has to internalize 18 rules
  before they know what "clean" means. Mitigation: the
  `why-rule-NN.md` documents are short and structured;
  newcomers can read them in order.
- **Top-level `sources` is a v0.2 schema break by addition.**
  v0.2 has `sources` only at snapshot level; v0.3 requires
  it at top level when `ste_status` ≠ `active`. This is a
  conditional requirement (a v0.2 document with no
  `ste_status` change remains valid under v0.3), but the
  schema does carry a new top-level field. v0.3's
  `additionalProperties: false` will reject documents that
  use the field accidentally; that rejection is the
  intended safety net.
- **Coord-provenance `method` enum is opinionated.** The
  enum (`geocoded | surveyed | interpolated | centroid |
  approximate | unknown`) is what v0.3 ships. Future methods
  (e.g. `lidar_extracted`) will need a v0.3.x enum
  addition. The cost: an enum change is a small break.
  Mitigation: the enum is documented in
  `docs/why-rules/why-rule-16.md`; the project's
  `additive/optional` tradition means contributors who
  invent a new method can request the enum bump via a
  follow-up RFC.
- **Bounded redirect depth = 8 is arbitrary.** Why 8, not
  4, not 16? The answer is "human history's deepest known
  merge chain is < 8; 8 is a comfortable upper bound".
  This is the kind of number that needs revisiting in
  5 years. Mitigation: app-level rule 14, not a schema
  constraint; can be changed without a version bump.
- **`ai_assisted` doubles the AI-provenance surface.** Two
  tiers (`ai_generated`, `ai_assisted`) instead of one means
  the display layer has to distinguish them. Mitigation: a
  demo CSS rule suffices; the schema change is small.
- **Migration script responsibility.** The string-to-object
  upgrade of `sources` is a migrator's choice; if the
  migrator is sloppy, "the city education gazette" gets
  written to `note` instead of `title`. Mitigation: the
  release ships with the migrator, and the migrator is
  fixture-tested (3 known strings → 3 known objects).

### 4.1 Reversibility

The change is **mostly reversible** at the schema level:
v0.2 documents remain valid under v0.3 (all changes are
additive/optional). A future v0.4 could deprecate the
string-shorthand form of `sources` (no-invention policy
applies to migration, not to deprecation). The
**irreversible** part is the schema's `ste_version: "0.3"`
const — once consumers have hard-coded that, removing the
const is a breaking change. This is by design.

## 5. Alternatives

### 5.1 Do nothing (v0.2 stays)

- The attribution ledger, AI-assisted provenance, and
  entity lifecycle all remain un-buildable. The
  `ste-attribution` profile stays a draft forever.
- **Trigger to revisit**: any of the five motivations in
  §2.1 becomes acute (e.g. a major contributor wants to
  import 10,000 OSM-derived schools, all with
  structured `sources` that v0.2 can't represent).

### 5.2 v0.3 = structured sources only

- Do §3.1 (sources) and §3.6 (contribution_meta slots) but
  not §3.2 / §3.3 / §3.4 / §3.5.
- **Pros**: smallest possible v0.3, fastest to ship.
- **Cons**: §3.2 (about_period) and §3.3 (ai_assisted) are
  requested by the demo's editorial workflow; §3.4
  (lifecycle) is needed for the merge dedup; §3.5
  (coord_provenance) was a near-miss incident. Deferring
  these pushes them to v0.4, which doubles the schema
  churn.
- **Trigger to revisit**: this alternative is a reasonable
  v0.3 if §3.2–§3.5 are not on the critical path; the
  RFC author believes they are (see §2.1).

### 5.3 Promote `ste_status` to a separate "lifecycle" profile

- Move §3.4 to a `ste-lifecycle` satellite profile; v0.3
  core stays leaner.
- **Pros**: smaller core, easier to back out.
- **Cons**: lifecycle is **fundamental** to identity
  resolution (UUIDs are not resolvable without
  `superseded_by`); making it a profile means consumers
  can't trust a `ste_id` without checking the profile.
  The author believes lifecycle belongs in core.
- **Trigger to revisit**: if a competing standard
  (e.g. OGC's) defines a compatible lifecycle model,
  STE could adopt and demote its own to a profile.

### 5.4 Untyped `coord_provenance.method` (string, not enum)

- Free-form method string; the validator only checks
  presence, not value.
- **Pros**: easy to extend (no enum change).
- **Cons**: silent divergence — one contributor says
  "geocoded", another says "geocoding", a third says
  "Geocoded". The linter and the dashboard can't tell
  these are the same. The enum is the floor.

### 5.5 Required `about_period` on every narrative

- Force every narrative to anchor to a period.
- **Pros**: every narrative is time-bounded; the
  side-by-side display is automatic.
- **Cons**: breaks the memoir-with-fuzzy-dates case
  (a 90-year-old narrator who says "in the 50s" cannot
  pin `about_period` precisely, and forcing them to
  guess is worse than letting them write the
  narrative un-anchored). §8 of the underlying
  proposal calls this out as an explicit non-goal;
  this RFC agrees.

## 6. Unresolved questions

1. **`ste_id` resolvability** — UUIDs are unique but not
   resolvable. The standalone lifecycle proposal §4 floats
   a two-stage approach: (1) a static `https://wonderingwu.github.io/ste-schema/id/<uuid>`
   redirect, (2) a `w3id.org/ste/<uuid>` persistent
   namespace. **Current leaning**: ship §3.4 without
   stage 1; add a follow-up RFC (RFC 0004-candidate) for
   stage 1. **Deadline**: this RFC can ship without
   stage 1; the follow-up RFC is a v0.3.x candidate.

2. **`coord_provenance` warning vs. error** — the
   underlying proposal says `centroid` / `approximate`
   emits a warning, not an error. The validator currently
   has no "warning" channel; everything is a pass / fail
   error. **Current leaning**: add a "warning" tier to
   the validator (a new return value, not a breaking
   change), and let app-level rule 16 be a warning. **Deadline**:
   can be added in the implementation PR, doesn't
   block this RFC.

3. **`ste-attribution` profile dependency** — RFC 0001
   provides the slots; the profile's semantics live in
   `docs/proposals/ste-attribution-profile.md`. If the
   profile doesn't ship in the same release, the slots
   are technically unused. **Current leaning**: ship
   the profile as part of the v0.3 release, behind
   `additionalProperties: false` on the core so its
   absence doesn't break consumers. **Deadline**:
   required for v0.3 release; tracked separately.

4. **CHANGELOG format** — the v0.2 → v0.3 release needs a
   `CHANGELOG.md` entry that lists every change
   (RFC-process §5). The entry is the implementer's job,
   not the RFC's, but the format should be agreed
   beforehand. **Current leaning**: Keep a Changelog
   1.1.0 format. **Deadline**: by the implementation
   PR.

5. **Migration of `ste:coord_confidence` tag** — the
   proposal deprecates the tag in favor of the
   `coord_provenance` field. The deprecation timeline
   (when does the tag stop being accepted?) is not in
   this RFC. **Current leaning**: accept the tag
   indefinitely (it's a `tags` key, `additionalProperties`
   allows it), with a deprecation note in
   `docs/why-rules/why-rule-06.md`. **Deadline**: low
   priority; can be a follow-up RFC.

## 7. Future possibilities

- **v0.3.x — Stage 1 of `ste_id` resolvability** (per
  Unresolved §6.1). Static `https://wonderingwu.github.io/ste-schema/id/<uuid>`
  redirect, following `superseded_by` once. Tracked as
  RFC 0004-candidate.
- **v1.0 — OGC JSON-FG profile** (RFC 0003-candidate; see
  `docs/profile/json-fg-mapping.md`). The v0.3 schema is
  a clean base for the profile: every new field is in
  `properties.ste.*` and survives the round-trip.
- **v1.0 — Structured evidence cross-validation**. v0.3
  sources are structured; v1.0 can require
  cross-source corroboration (two snapshots citing the
  same structured source = detectable).
- **v1.0 — Event model** (proposed in
  `docs/proposals/v0.3-entity-lifecycle.md`'s adjacent
  thread). v0.3's `ste_status` is the first step; v1.0
  promotes it to a first-class `Event` type with
  participant lists, time ranges, and causal edges.
- **v1.x — Polygon geometry**. Deferred from v0.3 per
  the underlying proposal §8. When OHM adds a polygon
  convention, STE picks it up.
