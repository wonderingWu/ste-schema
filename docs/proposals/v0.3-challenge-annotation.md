# Proposal: Challenge / Annotation Profile `ste-challenge` v0.1 (draft)

> Status: **draft profile** — 2026-08-27. Satellite of the STE core schema;
> does not change `ste_version`. Implements the data carrier for Ethics
> Charter **R4 (质疑权)**, which today has no schema home ("平台 v1" placeholder).
>
> Profile convention (per project policy): narrow core + satellite profiles.
> A challenge is NOT part of the entity document; it is a separate record that
> *points at* an entity, snapshot, narrative, or evidence item.

## 1. Semantics (from R4)

- Any user may challenge any data. A challenge is itself data: it must carry
  a reason and evidence (or explicitly point at missing evidence), is publicly
  visible, and renders **side by side** with the challenged content.
- A pure opinion objection without evidence does not constitute a challenge
  in the rule sense (`kind: "note"` exists for those, and platforms may hide
  them from the default evidence view).

## 2. Record shape (draft JSON Schema sketch)

```jsonc
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "$id": "https://wonderingwu.github.io/ste-schema/profiles/ste-challenge/0.1/schema.json",
  "title": "ste-challenge",
  "type": "object",
  "required": ["challenge_id", "profile_version", "target", "kind", "reason",
               "created_by", "created_at", "status"],
  "properties": {
    "challenge_id":   { "type": "string", "pattern": "^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$" },
    "profile_version":{ "const": "0.1" },
    "target": {
      "type": "object",
      "required": ["ste_id"],
      "properties": {
        "ste_id":          { "type": "string" },
        "snapshot_index":  { "type": "integer", "minimum": 0 },
        "narrative_index": { "type": "integer", "minimum": 0 },
        "evidence_index":  { "type": "integer", "minimum": 0 },
        "json_pointer":    { "type": "string", "pattern": "^/" }
      },
      "additionalProperties": false
    },
    "kind":   { "enum": ["challenge", "corroboration", "note"] },
    "reason": { "type": "string", "minLength": 1 },
    "evidence": { "$ref": "../../../v0.2/schema.json#/definitions/evidence_item" },
    "claims_missing_evidence": { "type": "boolean" },
    "created_by": { "type": "string",
      "pattern": "^(user:[A-Za-z0-9._-]+|anon:[A-Za-z0-9._-]+|agent:[A-Za-z0-9._-]+|system:[A-Za-z0-9._-]+|community)$" },
    "created_at": { "type": "string", "format": "date-time" },
    "status": { "enum": ["open", "answered", "resolved", "dismissed"] },
    "resolution": {
      "type": "object",
      "properties": {
        "outcome":    { "enum": ["upheld", "rejected", "data_corrected"] },
        "resolved_by":{ "type": "string" },
        "resolved_at":{ "type": "string", "format": "date-time" },
        "note":       { "type": "string" }
      },
      "additionalProperties": false
    }
  },
  "allOf": [
    { "if": { "properties": { "kind": { "const": "challenge" } } },
      "then": { "anyOf": [
        { "required": ["evidence"] },
        { "properties": { "claims_missing_evidence": { "const": true } },
          "required": ["claims_missing_evidence"] }
      ] } },
    { "if": { "properties": { "status": { "enum": ["resolved", "dismissed"] } } },
      "then": { "required": ["resolution"] } }
  ]
}
```

## 3. Rules

- Exactly one of `snapshot_index` / `narrative_index` / `evidence_index` /
  `json_pointer` may be present (default: the whole entity).
- `kind=challenge` requires `evidence` OR `claims_missing_evidence: true`
  (R4: "指出证据缺失" is a valid challenge).
- `dismissed` is a **platform/committee** outcome and must name `resolved_by`;
  the challenge record itself is never deleted (R6 tombstone logic applies to
  challenges as to narratives).
- `corroboration` reuses the same shape so that supporting evidence can be
  attached to disputed items symmetrically (Belief 4: display both sides).

## 4. Open questions for review

1. Should `resolution` be a single object or an append-only `resolution_log[]`
   (appeals per charter §3.2)? Leaning log, but KISS for v0.1.
2. Does `evidence` reuse the v0.2 evidence definition by `$ref`, or get copied
   to keep the profile self-contained? `$ref` shown above (relative to the
   profile's declared `$id` at `profiles/ste-challenge/0.1/schema.json`, three
   directory levels deep, hence `../../../`); copying is more portable across
   repos.
3. Index-based targeting is fragile under timeline edits; `json_pointer` is
   precise but brittle too. Consider snapshot content-hash addressing in v0.2
   of this profile.
