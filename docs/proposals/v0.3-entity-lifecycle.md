# Proposal: Entity Lifecycle & ID Resolution (target: v0.3)

> Status: **draft proposal** — 2026-08-27. Not yet part of any released schema version.
> Motivation: STE v0.2 gives every entity a stable UUID, but says nothing about
> what happens when entities merge, split, or are withdrawn — a routine case in
> historical geography (one school splits into two; two schools merge; a record
> turns out to be a duplicate). It also gives no resolution strategy for the UUID.

## 1. New top-level field: `ste_status`

| Value | Meaning |
|---|---|
| `active` | Normal, current record (default when absent) |
| `merged` | This entity ceased to exist as a record because it was merged into another STE entity |
| `split` | This entity was split into two or more successor entities |
| `deprecated` | Record withdrawn (duplicate, created in error, or superseded for data-quality reasons) |

Rules:

- `ste_status` is orthogonal to snapshot-level `status` (`demolished` etc.):
  snapshot status describes **the place in the world**; `ste_status` describes
  **the record in the dataset**.
- `merged` / `split` / `deprecated` records are **tombstones, not deletions**
  (consistent with Ethics Charter R6): the record stays readable, is excluded
  from default map/search rendering, and keeps its full history.

## 2. Relationship fields

```jsonc
{
  "ste_status": "merged",
  "superseded_by": ["<uuid-of-surviving-entity>"],
  "ste_status_changed_at": "2026-08-27T08:00:00Z",
  "ste_status_reason": "Duplicate of Q-sourced record; timeline merged."
}
```

- `superseded_by`: array of `ste_id`s. REQUIRED when `ste_status` is
  `merged`, `split`, or `deprecated`-as-duplicate; forbidden when `active`.
- `supersedes`: array of `ste_id`s, the inverse pointer on the surviving
  entity. Optional but recommended; applications must treat `superseded_by`
  as authoritative and `supersedes` as a denormalized cache (same rule as
  `name`: on conflict, the tombstone side wins).
- Referenced IDs must exist in the dataset or carry a `note` explaining the
  external target (application-level rule; schema checks format only).

## 3. Validation consequences (application-level checklist additions)

- A `merged`/`split`/`deprecated` entity MUST NOT gain new timeline snapshots
  after `ste_status_changed_at` (platform-side enforcement).
- Redirect loops are forbidden: following `superseded_by` chains must
  terminate at an `active` entity within a bounded depth (suggest ≤ 8).
- Consumers resolving an ID that lands on a tombstone SHOULD follow
  `superseded_by` and indicate the redirect in the UI.

## 4. ID resolution strategy (policy, not schema)

UUIDs are unique but not resolvable. Proposal, in two stages:

1. **Stage 1 (now)**: document that the canonical URI form is
   `https://wonderingwu.github.io/ste-schema/id/<uuid>`; a static redirect
   page (or dataset lookup) resolves to the entity's current home, following
   `superseded_by` once.
2. **Stage 2 (when third-party producers exist)**: register a namespace with
   a persistent identifier service (w3id.org pattern, e.g.
   `https://w3id.org/ste/<uuid>`) so identifiers survive repository moves.

## 5. Backwards compatibility

- All new fields optional; v0.2 documents remain valid.
- No change to `ste_version` — these fields land in v0.3 with
  `const: "0.3"` and the usual en/zh parity + negative fixtures.
