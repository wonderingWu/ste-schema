# Proposal: STE Core v0.3 — Structured Sources & Consolidated Upgrade

> Status: **draft proposal** — 2026-08-28. Consolidates and supersedes the
> standalone `v0.3-entity-lifecycle.md` (kept for history; §4 here is
> authoritative). Companion satellite profiles (NOT part of this core bump):
> `v0.3-challenge-annotation.md` and `ste-attribution-profile.md`.
>
> **Foundation first**: §1 structured sources is the layer everything else
> (attribution ledger, lifecycle auditability, narrative provenance) builds on.

## 0. Package contents & versioning

- This package bumps the core to `ste_version: "0.3"` (`const`-locked, same
  rule as v0.2). All changes are **additive/optional except where stated**;
  v0.2 documents remain valid under v0.2 and migrate mechanically (§6).
- Tradition kept: every new rule ships with ≥1 negative fixture; en/zh
  structural parity is CI-enforced; the reference validator gains matching
  application-level checks with the rule-count constant updated crosswise.

## 1. Structured source objects (THE FOUNDATION)

### 1.1 Motivation

v0.2 `sources` is an array of free strings (`["市教育志"]`). That satisfies
R1 ("no source, no entry") but nothing more: sources cannot be de-duplicated,
cross-checked, cited in an attribution ledger, or validated for liveness.
Every planned feature — the ste-attribution manifest, external_id liveness
checks, community corroboration — needs machine-readable sources.

### 1.2 Design

```jsonc
// v0.3 source object (definition source_object)
{
  "type": "archive",          // REQUIRED, enum below
  "title": "北京市教育志",     // REQUIRED, non-empty
  "author": "…",              // optional
  "publisher": "…",           // optional (档案馆/出版社/机构/平台)
  "date": "1998",             // optional, ohm_date — publication/issue date
  "url": "https://…",         // optional, format uri
  "archive_ref": "J001-2-334",// optional — catalogue/call/file number
  "accessed_at": "2026-08-28T08:00:00Z", // optional, date-time (web sources)
  "note": "…"                 // optional
}
```

`type` enum: `archive | official | news | book | map | photo | oral_history | dataset | web | other`.

### 1.3 Rules

- `sources` items may be **string (legacy shorthand) or object** in v0.3;
  a string `S` normalizes to `{ "type": "other", "title": S }`. minItems 1
  unchanged (R1 untouched).
- At least one of `url` / `archive_ref` / `publisher` SHOULD be present
  (application-level warning, not schema error — oral history may have
  none, identified instead by `title` + `note`).
- `type=web` ⇒ `url` REQUIRED (inline if/then); `accessed_at` recommended.
- `type=oral_history` ⇒ the snapshot/narrative SHOULD carry R2 author
  metadata (application-level cross-check).
- baidu_baike rule unchanged: a Baike URL may appear as `url`, content
  MUST NOT be ingested (license).

### 1.4 What this unlocks

- **ste-attribution ledger**: contributor × contribution × *citable source*
  triples become mechanically aggregatable.
- **Source liveness checks**: `url` + `accessed_at` enable periodic
  dead-link sweeps (pairs with application rule 09).
- **Corroboration counting**: two snapshots citing the *same* structured
  source is detectable; independent sourcing becomes measurable.

## 2. Narrative time anchor (`about_period`)

Narratives currently attach to the whole entity — "this memoir is about the
school *in the 1980s*" is inexpressible.

```jsonc
// optional field on narrative_entry
"about_period": { "start": "1980", "end": "1989" }   // ohm_date both ends
```

- `start` REQUIRED when `about_period` present; `end` optional (open-ended
  means "until the narrator's knowledge ends").
- Semantics: the period the narrative *refers to*, independent of when it
  was written. Display rule: narratives render alongside the matching
  timeline snapshots; platforms MUST NOT present an unanchored narrative as
  describing the present.
- Application-level: `end >= start` after granularity normalization (same
  comparison rules as timeline).

## 3. Narrative & description provenance: human+AI mixed workflows

v0.2 enums are single-choice (`manual` / `ai_generated` / …), but the real
workflow is often "AI draft → human verifies". v0.3:

- Add enum value **`ai_assisted`** to `description_provenance` and to
  narrative `source_of_knowledge`.
- `ai_assisted` ⇒ REQUIRED: `ai_model` (same rule as ai_generated) AND
  **`reviewed_by`** (`actor_id`, must be `user:` or `community`, i.e. a
  human/accountable party — never `agent:`) + `reviewed_at` (date-time).
- Display rule (R3 unchanged in spirit): ai_assisted renders with the same
  visual distinction as ai_generated, plus the reviewer identity. The
  self-reported `confidence` remains REQUIRED and labeled as generator-reported.

This closes the loophole where "a human glanced at it" laundered AI text
into `manual`.

## 4. Entity lifecycle (consolidated from v0.3-entity-lifecycle.md)

Adopted from the standalone proposal: `ste_status` (`active` default /
`merged` / `split` / `deprecated`), `superseded_by`, `supersedes`
(denormalized inverse; tombstone side wins on conflict),
`ste_status_changed_at`, `ste_status_reason`; tombstones never deleted.
Application rules adopted unchanged: no new timeline snapshots after
`ste_status_changed_at` (platform-enforced), and consumers resolving a
tombstone SHOULD follow `superseded_by` and indicate the redirect.

**Deliberate changes vs. the standalone proposal (called out, per review):**

1. `superseded_by` is REQUIRED for `merged` / `split` /
   `deprecated`-as-duplicate, and FORBIDDEN when `active`. A record
   deprecated as *created in error* has no successor to point at — it carries
   `ste_status_reason` only (this restores the standalone proposal's scope;
   an earlier draft of this section had silently widened it to all
   non-active statuses).
2. Redirect chains MUST terminate at an `active` entity within depth ≤ 8 —
   hardened from the standalone proposal's "suggest ≤ 8", because an
   unbounded chain makes consumers' resolution behavior undefined.
3. **Addition**: every `ste_status` change is itself a sourced event. When
   `ste_status` ≠ active, **top-level** `sources` (structured, §1) and
   `contributed_by` are REQUIRED — note these are *new top-level fields*:
   v0.2 has `sources`/`contributed_by` only at snapshot level, so the v0.3
   core schema gains both at the root. A merge without a source is exactly
   the kind of edit R1 exists to catch.

## 5. Coordinate provenance (field lesson, 2026-08-26/27)

Two incidents motivate this: 6 schools geocoded by guesswork (caught by the
owner), and OSM `way center` centroids silently imported as representative
points.

```jsonc
// optional, entity level and per-snapshot (snapshot wins when both)
"coord_provenance": {
  "method": "geocoded",   // REQUIRED enum: geocoded | surveyed | interpolated | centroid | approximate | unknown
  "source": { …source_object… },  // optional structured source (§1)
  "note": "OSM way centroid, not a curated point"  // optional
}
```

- Rules: `method=centroid` or `approximate` ⇒ validator emits a warning and
  UIs SHOULD display low-precision styling (replaces the ad-hoc
  `ste:coord_confidence` tag with a first-class field; the tag remains valid
  but deprecated in docs).
- `method` is about *how the point was obtained*, orthogonal to
  `confidence` (how sure the contributor feels).

## 5A. `contribution_meta` field slots (extension point for profiles)

v0.2's `contribution_meta` is `additionalProperties: false`, which means NO
satellite profile can attach attribution signals without a core change
(caught in review). v0.3 therefore adds three OPTIONAL field slots to the
core definition — the core provides the *slots*, the `ste-attribution`
profile defines their *semantics* (ledger generation, claim flows):

```jsonc
"contribution_type": "create",          // enum: create | edit | corroborate |
                                        //   geolocate | oral_history | translate | review
"identity": {                           // at most one of the two sub-fields
  "key_fingerprint": "pgp:9F3C…"        // pattern ^(pgp|did):.+$
  // or: "claim_commitment": "sha256:…" // pattern ^sha256:[0-9a-f]{64}$
},
"rights": {
  "ai_training": "inherit"              // enum: inherit | opt_in
}
```

Inline constraints:

- `identity` allows at most one of `key_fingerprint` / `claim_commitment`.
- `contribution_type=oral_history` ⇒ `rights.ai_training=opt_in` FORBIDDEN
  (R9: oral history is permanently excluded from AI training, no opt-in).
- All three slots optional everywhere; documents without them remain valid.

(Why slots live in core: profile documents must pass the core validator;
with a closed `contribution_meta`, any profile-defined field would fail
validation. Opening `additionalProperties` wholesale was rejected — explicit
slots keep one-negative-fixture-per-rule enforceable.)

## 6. Migration (v0.2 → v0.3)

1. `ste_version`: `"0.2"` → `"0.3"`.
2. `sources`: strings keep working (normalization rule §1.3); migrators MAY
   upgrade known patterns (URL strings → `{type:"web", url, title}`) but MUST
   NOT invent `date`/`author` (no-invention policy, same as the OSM importer).
3. No other v0.2 field changes meaning. The v0.3 feature areas (§1–§5A) are
   independent: a consumer may implement sources-only and ignore the rest.
4. Migration script + fixtures ship with the release, mirroring
   `dataset/migrate-77.js` practice (57 half-open → closed date fixes were
   the v0.1→v0.2 precedent).

## 8. Explicit non-goals (KISS guardrails)

- No pricing, royalty, or token mechanics anywhere in core (reserved for the
  `ste-attribution-profile.md` satellite profile: the ledger is data, the
  economics are not).
- No required `about_period` (would break the memoir-with-fuzzy-dates case).
- No geometry/footprint support (polygons stay an OHM-side concern; STE
  remains a point + timeline archive).
